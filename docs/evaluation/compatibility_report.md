# CoVibe - Cross-Browser Compatibility Report & Testing Checklist
**ระบบความเข้ากันได้และการทดสอบอุปกรณ์เคลื่อนที่สำหรับ iOS Safari + Android Chrome**

เอกสารนี้ระบุรายละเอียดเกี่ยวกับข้อจำกัดทางเทคนิคของแพลตฟอร์มเคลื่อนที่ (Mobile Browsers), แนวทางการหลีกเลี่ยง (Workarounds), และชุดทดสอบความเข้ากันได้ (Compatibility Test Cases) เพื่อให้บรรลุเกณฑ์การส่งมอบงาน (Exit Criteria) ของ Phase 0 ในโปรเจกต์ CoVibe

---

## 1. ข้อมูลภาพรวมเชิงสถาปัตยกรรม (Application Tech Stack)
แอปพลิเคชัน CoVibe พัฒนาขึ้นโดยอิงตามเทคโนโลยีหลักดังนี้:
* **Frontend**: React (TypeScript) + Vite
* **Realtime Sync**: WebSockets (ผ่าน CoVibe Realtime Server พอร์ต `8787` หรือเทียบเท่า)
* **Audio/Video Playback**: YouTube IFrame Player API + HTML5 Web Audio API
* **Voice Chat**: WebRTC Peer-to-Step/Peer-to-Peer (Voice Signal exchange)

---

## 2. ข้อจำกัดทางเทคนิคและแนวทางการแก้ไข (Platform Constraints & Workarounds)

### 2.1 ข้อจำกัดการเล่นอัตโนมัติ (Autoplay Restrictions)
เบราว์เซอร์บนระบบปฏิบัติการมือถือ (โดยเฉพาะ iOS Safari และ Android Chrome) มีนโยบายจำกัดการเล่นเสียงอัตโนมัติที่เข้มงวดเพื่อประหยัดข้อมูลมือถือและป้องกันการรบกวนผู้ใช้
* **พฤติกรรมข้อจำกัด**: เบราว์เซอร์จะไม่ยอมรับคำสั่ง `.play()` หรือการโหลดไฟล์เสียง/วิดีโอที่มีเสียง (Unmuted) โดยตรง หากไม่เกิดขึ้นจาก **การแตะสัมผัสจริงของผู้ใช้ (User Gesture/Interaction)** เช่น การคลิกปุ่ม
* **ผลกระทบ**: เมื่อโฮสต์เริ่มเล่นเพลง สมาชิกที่เข้าร่วมห้องใหม่จะไม่สามารถเล่นเสียงตามแบบอัตโนมัติได้ทันที
* **แนวทางการแก้ไข (Workaround)**:
  1. สร้าง **Onboarding Modal** หรือ **Overlay** ในช่วงเริ่มต้นเมื่อเชื่อมต่อห้องใหม่ เพื่อให้ผู้ใช้อย่างน้อยต้องทำ 1 Action (เช่น กดปุ่ม "คลิกเพื่อเชื่อมต่อและเล่นเพลง")
  2. ระหว่างที่ผู้ใช้คลิกปุ่มดังกล่าว ให้โปรแกรมทำภารกิจ "ปลดล็อก" โดยสั่งให้สร้างและสั่งเล่น (Resume) `AudioContext` ว่างๆ หรือส่งคำสั่งเล่นเสียงความยาว 0.1 วินาทีแบบปิดเสียงไว้ก่อน เพื่อให้เบราว์เซอร์อนุญาตให้โค้ดสั่งเล่นสื่อในครั้งถัดๆ ไปผ่าน WebSocket ได้

### 2.2 ข้อจำกัดการรันเบื้องหลัง (Background Execution & Throttling)
เพื่อควบคุมการใช้งานพลังงานและแบตเตอรี่บนระบบเคลื่อนที่ เบราว์เซอร์จะลดการทำงานของสคริปต์เมื่อผู้ใช้ย่อหน้าต่างหรือล็อกหน้าจอ
* **พฤติกรรมข้อจำกัด**:
  * **iOS Safari**: จะตัดการเชื่อมต่อ WebSocket หรือทำการ "แช่แข็ง (Freeze)" การประมวลผล Javascript (รวมถึงสัญญานเวลา `setInterval` / `setTimeout`) ภายใน 5-15 วินาทีหลังจากย้ายแอปไปไว้เบื้องหลัง (Background/Locked Screen)
  * **Android Chrome**: จะจำกัดอัตราการประมวลผลเวลา (Timer Throttling) ให้ทำงานเพียง 1 ครั้งต่อนาทีสำหรับแท็บที่ไม่ได้แอคทีฟ
* **ผลกระทบ**: ตัวเลขเวลาซิงค์ (Playback Drift) จะเพี้ยนไปอย่างรวดเร็วเมื่อล็อกหน้าจอ และเสียงจะหยุดหรือดีเลย์เมื่อเปิดจอกลับขึ้นมาใหม่
* **แนวทางการแก้ไข (Workaround)**:
  1. ใช้ **Page Visibility API** (`document.visibilityState` / `visibilitychange`) เพื่อตรวจจับเมื่อผู้ใช้เปิดจอกลับเข้ามาใหม่ จากนั้นให้ส่งคำขอซิงค์เวลาใหม่ไปยังเซิร์ฟเวอร์แบบทันที (Fast Sync Catch-up)
  2. แนะนำผู้ใช้งานในหน้าเว็บให้เปิดแท็บหลักไว้เสมอ หรือหากจำเป็นต้องใช้แบบล็อกหน้าจอในอนาคต แนะนำให้พัฒนาแอปพลิเคชันรูปแบบ Native (Xcode / Android SDK) เพื่อรัน Background Audio Session

### 2.3 การทำงานของ Wake Lock API
ป้องกันไม่ให้หน้าจอดับ (Screen Sleep) ระหว่างฟังเพลงร่วมกับเพื่อน
* **พฤติกรรมข้อจำกัด**:
  * **Android Chrome**: รองรับ `navigator.wakeLock` เต็มรูปแบบ แต่หน้าเว็บต้องมีสถานะ Active เสมอ
  * **iOS Safari**: รองรับตั้งแต่ iOS 13.7+ เป็นต้นไป แต่จะทำงานได้เฉพาะเมื่อมีการป้อนสิทธิ์การเล่นเสียง/วิดีโอ (Media Element Playback) ควบคู่ไปด้วย และจะสูญเสียสิทธิ์ทันทีที่แท็บเบราว์เซอร์หลุดโฟกัสหรือเปิดโหมดประหยัดพลังงาน (Low Power Mode)
* **แนวทางการแก้ไข (Workaround)**:
  - ใช้ Try-Catch ครอบคำขอ `wakeLock` และตรวจสอบความพร้อมผ่านฟังก์ชันเช็กสิทธิ์เสมอ หากเกิดข้อผิดพลาด ให้ใช้วิธีเปลี่ยน UI แนะนำผู้ใช้ตั้งค่า Screen Timeout บนมือถือแทน
